# Design: Sistema i18n con traduzione LLM

**Data:** 2026-06-24
**Branch:** feature/various-small-fixes
**Stack:** Next.js 15 App Router · TypeScript · Supabase · next-intl · Claude API

---

## Sommario

Sistema di internazionalizzazione che supporta 30+ lingue senza file di traduzione manuali. Le stringhe UI sono mantenute dal developer in un file sorgente; i contenuti dinamici (label menu, ecc.) sono gestiti dall'admin. Un'unica chiamata batch a Claude genera tutte le traduzioni e le salva in Supabase. La lingua è per-utente, salvata nel profilo, senza prefisso nell'URL.

---

## 1. Architettura

```
messages/source.json          ← stringhe UI sorgente (dev, in git)
         │
         ▼
Supabase: translations         ← tutte le traduzioni generate da LLM
  (namespace, key, locale, value, source_text, source_locale)
         │
         ▼
Root layout (server)           ← legge locale dal profilo utente
         │                       carica messaggi dal DB per quel locale
         ▼
NextIntlClientProvider         ← inietta i messaggi nel React tree
         │
         ├── useTranslations()  ← componenti client
         └── getTranslations()  ← server components
```

**Principi chiave:**
- Nessun prefisso URL (`/en/...`). Il locale viene dalla sessione utente.
- `source.json` è il fallback per chiavi non ancora tradotte — nessun crash, nessuna stringa vuota.
- Le traduzioni LLM sono generabili/rigenerabili on-demand dall'admin.
- Le stringhe dinamiche (menu label) usano lo stesso sistema delle stringhe UI.

## 2. Modello dati

### Tabella `translations`

```sql
CREATE TABLE translations (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  namespace     text NOT NULL,
  key           text NOT NULL,
  locale        text NOT NULL,
  value         text NOT NULL,
  source_text   text,
  source_locale text,
  generated_at  timestamptz DEFAULT now(),
  UNIQUE (namespace, key, locale)
);
```

**Namespacing:**
| namespace | key esempio              | sorgente            |
|-----------|--------------------------|---------------------|
| `ui`      | `nav.save`               | `source.json`       |
| `ui`      | `admin.menuBuilder.title`| `source.json`       |
| `menu`    | `item.<uuid>.label`      | `menu_items.label`  |

### Tabella `locales`

```sql
CREATE TABLE locales (
  code        text PRIMARY KEY,   -- 'en', 'fr', 'de', 'zh', ...
  name        text NOT NULL,       -- 'English', 'Français', ...
  native_name text NOT NULL,       -- 'English', 'Français', '中文', ...
  active      boolean DEFAULT true,
  flag_emoji  text,                -- '🇬🇧', '🇫🇷', ...
  sort_order  int DEFAULT 0
);
```

Seed iniziale: ~50 lingue comuni pre-caricate. L'admin attiva quelle desiderate.

### Campo `locale` su `users`

```sql
ALTER TABLE users ADD COLUMN locale text REFERENCES locales(code);
```

Default `NULL` → fallback alla lingua sorgente.

## 4. Runtime: caricamento traduzioni

### Root layout (server)

```tsx
// app/layout.tsx
import { auth } from '@/lib/auth'
import { loadMessages } from '@/lib/i18n-server'
import { NextIntlClientProvider } from 'next-intl'

export default async function RootLayout({ children }) {
  const session = await auth()
  const locale = session?.user?.locale ?? 'source'
  const messages = await loadMessages(locale)

  return (
    <html>
      <body>
        <NextIntlClientProvider locale={locale} messages={messages}>
          {children}
        </NextIntlClientProvider>
      </body>
    </html>
  )
}
```

### `loadMessages(locale)` — `lib/i18n-server.ts`

`source.json` usa struttura nested (`{ nav: { save: "Salva" } }`); il DB salva chiavi flat (`nav.save`). `loadMessages` converte le chiavi flat del DB in nested prima del merge.

```ts
export async function loadMessages(locale: string) {
  // source.json è già nested — next-intl lo consuma direttamente
  const source = (await import('@/messages/source.json')).default

  if (!locale || locale === 'source') return source

  const { data } = await supabase
    .from('translations')
    .select('key, value, namespace')
    .eq('locale', locale)

  if (!data?.length) return source

  // Converte chiavi flat DB → nested, poi merge sopra source (fallback)
  const dbNested = flatKeysToNested(data)   // { nav: { save: "Save" }, ... }
  return deepMerge(source, dbNested)
}
```

`flatKeysToNested` converte `[{ key: 'nav.save', value: 'Save' }]` → `{ nav: { save: 'Save' } }`. `deepMerge` sovrascrive il source con i valori DB dove presenti, lascia il fallback source per le chiavi mancanti.

### Uso nei componenti

**Server component:**
```tsx
import { getTranslations } from 'next-intl/server'

export default async function MenuBuilderPage() {
  const t = await getTranslations('admin.menuBuilder')
  return <h1>{t('title')}</h1>
}
```

**Client component:**
```tsx
'use client'
import { useTranslations } from 'next-intl'

export function SaveButton() {
  const t = useTranslations('nav')
  return <button>{t('save')}</button>
}
```

**Fallback:** chiave senza traduzione → mostra il valore da `source.json`. Mai stringa vuota o crash.

## 5. Pipeline di traduzione LLM

### API route: `POST /api/admin/translate`

Richiede ruolo `admin`. Body:

```json
{
  "locales": ["en", "fr", "de", "es", "zh"],
  "overwrite": false
}
```

### Algoritmo

1. **Raccolta sorgenti:**
   - Appiattisce `source.json` → `[{ namespace: 'ui', key: 'nav.save', value: 'Salva' }, ...]`
   - Legge `menu_items.label` → `[{ namespace: 'menu', key: 'item.<uuid>.label', value: '...' }, ...]`

2. **Filtro** (se `overwrite: false`): esclude chiavi già presenti in `translations` per tutti i locale target.

3. **Chunking:** gruppi da 100 stringhe per chiamata Claude.

4. **Prompt Claude:**

```
Traduci le seguenti stringhe JSON nei locale indicati.
Rileva automaticamente la lingua sorgente.
Rispondi SOLO con JSON valido, nessun testo aggiuntivo.

Formato risposta:
{
  "en": { "nav.save": "Save", "nav.cancel": "Cancel" },
  "fr": { "nav.save": "Enregistrer", "nav.cancel": "Annuler" }
}

Locale target: en, fr, de, es, zh, ...

Stringhe da tradurre:
{ "nav.save": "Salva", "nav.cancel": "Annulla" }
```

5. **Salvataggio:** upsert in `translations` per ogni `(namespace, key, locale)`.

6. **Risposta:** `{ translated: N, locales: [...], skipped: M, errors: [] }`

### Gestione errori

- Chunk fallito → retry una volta, poi registra le chiavi fallite in `errors[]`
- JSON malformato nella risposta LLM → retry del chunk
- Timeout → restituisce risultato parziale con le chiavi già tradotte

### Integrazione Menu Builder

Nessuna modifica al form esistente. Al salvataggio di una voce menu, il server action registra automaticamente la label come stringa traducibile in `translations` con `namespace='menu'` e `locale=source`. "Traduci tutto" la include nel prossimo batch.

### Profilo utente

Dropdown **"Lingua"** aggiunto al form profilo esistente (`ProfileForm.tsx`). Lista delle sole lingue attive. Al salvataggio aggiorna `users.locale`; il client fa `router.refresh()` per ricaricare i messaggi nella nuova lingua.

## 7. Scope: cosa viene tradotto e cosa no

| Contenuto | Tradotto | Motivo |
|-----------|----------|--------|
| Stringhe UI (`source.json`) | ✅ | Dev-managed, sempre nel sistema |
| Label menu (`menu_items.label`) | ✅ | Contenuto di sistema |
| Dati inseriti dagli utenti (nomi, descrizioni) | ❌ | Contenuto utente, fuori scope |
| Messaggi di errore API | ✅ | Aggiunti a `source.json` dal developer |
| Contenuto email (template) | ❌ | Fuori scope v1 |
